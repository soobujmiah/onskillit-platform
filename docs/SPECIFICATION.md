## Product goals and non-goals

Goals: visitors can understand verified offerings; students can enroll and learn; coordinators can run training batches; authorized editors can publish accurate content; staff can track client relationships; sensitive actions are traceable; the platform works on mobile and in Bangla/English as approved. The founding partner's quality ambition is that the site should be **a marvel of the team's work**: original art direction, exceptional clarity and polish, and operational depth must all be visible. Success measures should be agreed before launch: qualified inquiries, enrollment completion, course progress, staff time saved, indexed valid pages and support response time.

V1 non-goals: bulk migration of existing WordPress content; native mobile apps; mandatory OTP/2FA; general marketplace; custom video streaming; arbitrary executable page-builder blocks; advanced project planning; automated payroll; invented testimonials. **Confirmed direction:** V1 payment must be complete enough for real use, including live online checkout as well as invoices, failed/pending states, refunds and reconciliation. Gateway activation still requires merchant eligibility, contract, tax/refund policy and owner approval.

## CMS and content governance

Manage pages, typed sections, navigation/header/footer, services, courses, programs, instructors, team/developers, testimonials, projects/portfolio, blog, FAQs, announcements, media, contact/socials, SEO, redirects and site settings. Section registry: hero, rich text, image/video, service/course/portfolio grid, team/instructor, testimonial, stats, FAQ, CTA, gallery, pricing, timeline, feature grid and contact. Each section has schema version, order, locale, visibility, references and optional schedule. Reusable sections are versioned. Private preview uses signed access. Revision rollback creates a new revision. No raw script/custom HTML in V1.

Publication workflow: draft → review → approved → published → archived; approval rules apply to homepage, legal, pricing and financial claims. Publish validation checks title/H1, alt text, metadata, canonical, working internal links, rights, source evidence and language completeness. Prevent template/demo content and unsupported claims with a quarantine state and review checklist. Media records contain original checksum, verified MIME, dimensions, derivatives, alt/caption, rights/consent and access class; private learning documents use short-lived authorized access.

## Identity, admin and RBAC

One `User` can hold student, client, instructor and staff roles. Candidate roles: platform owner, security admin, content admin, editor, reviewer, training manager, instructor, sales, finance, support, student, client user. “Super Admin / Admin / Sub-Admin” are labels over explicit action/resource/scope permissions, not a hard-coded single-admin tree. Multiple owner/admin accounts are supported. Delegation cannot grant powers beyond the grantor's approved scope. Deny by default and enforce on every server query/command; UI hiding is insufficient. Separate publish, user/role, finance, security and settings permissions. Log grants, revocations and sensitive actions.

**Confirmed V1 choice:** registration accepts either email **or** mobile plus password; both may be supplied. Normalize and uniquely index each supplied contact. Track verification state for future OTP/email/phone verification but require no OTP now. An unverified contact is never represented as verified and cannot alone authorize sensitive invitations, financial changes or disclosure. Contact squatting and rightful-owner recovery must be handled in the security procedure. Use modern password hashing, secure revocable sessions, rate limits, generic reset response and hashed single-use reset tokens. Email accounts may use self-service email reset when mail delivery is configured. Mobile-only accounts use **staff-assisted recovery** until OTP exists: a restricted support request, identity proofing under a separately approved procedure, no disclosure of existing password, no staff-selected permanent password, second-person approval for high-risk/privileged accounts, one-time short-lived reset handoff, session revocation, user notification where possible and a complete audit trail. Staff must not use easily guessed personal facts or security questions as proof. The exact proofing evidence and retention rules require security/privacy approval before launch. [OWASP forgot-password guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html). Account states: active/inactive/suspended/deletion-pending. Future 2FA is an assurance factor, not a separate identity.

## LMS, TMS and enrollment

`Course` owns learning outcomes; `CourseEdition` freezes curriculum at enrollment; `Module → Lesson → Asset`; `Assessment → Submission → Grade`; progress comes from completion events. TMS `Program` and `Batch` schedule `TrainingSession`, assign instructor/classroom/online link, track capacity, attendance, assessment events and results. A batch can deliver a course edition so LMS and TMS share one learner identity and enrollment history. Attendance is distinct from online lesson progress. Enrollment states: requested, pending-payment, admitted, waitlisted, active, completed, cancelled, transferred. Enforce capacity transactionally; retain transfer and cancellation history. Certificate eligibility/issuer policy requires owner approval. V1 supports online/offline/hybrid metadata and basic quizzes/assignments; proctoring and SCORM require separate evidence.

Student portal: profile, enrolled courses/training, lessons/schedule, progress, submissions/results, certificates when authorized, invoices/payments, notices, support/settings. Instructor portal: assigned curriculum, attendance, grading and material submission. One person with multiple roles uses one login and context switch. Client portal V1 should expose only records linked to the user's client account; staff-only notes never appear there.

## Services, CRM, payment and notifications

Lead lifecycle: inquiry → qualified → opportunity/proposal → won/lost; won links a `ClientAccount`, contacts and optional service engagement/project. Activities, notes, documents, assigned staff, follow-ups, support requests and history are scoped and timestamped. Public service copy and internal delivery records are separate. Invoice, payment intent, transaction, refund and reconciliation are distinct entities. Payment provider adapter must verify signed callbacks, amount/currency/reference and idempotency; never store card details. Offline/manual payment needs evidence and approval. Provider, tax, refund and legal terms remain open. Notifications use event+channel adapters: in-app and transactional email where configured in V1; SMS and messaging integrations later. Separate transactional notices from consent-based marketing.

## SEO, search, analytics and localization

Render crawlable public content on the server. CMS controls title, description, canonical, index/noindex, OG, image alt, redirects and appropriate structured data (Organization, Service, Course, Article, Breadcrumb). Generate sitemaps only from approved indexable pages; noindex drafts, portals, admin, internal search and thin duplicates. Define 404/410/301 from audited URLs. Verify local SEO address and credentials before markup. See [Google SEO guidance](https://developers.google.com/search/docs/fundamentals/seo-starter-guide) and [structured data policies](https://developers.google.com/search/docs/appearance/structured-data/sd-policies).

Public search covers approved services/courses/articles/portfolio; staff search is permission-filtered. Start with database search only after a Bangla/English relevance evaluation; add a dedicated engine if corpus and scale warrant it. Public analytics should minimize personal data; business metrics derive from enrollment, lead and finance events with documented formulas.

**Confirmed bilingual requirement:** launch with complete Bangla and English versions, matching the portfolio's language-purity principle. Every authored visible string on the Bangla version—including navigation, brand wording, course/service copy, forms, validation, errors, empty states, admin, portals, notifications, image alt text, accessible labels and SEO metadata—uses Bangla script and natural Bangla phrasing, with no English letters. The English version contains no Bengali characters. Digits follow the active locale. Proper names, email addresses, URLs, code and external identifiers are data rather than authored prose; display them only where functional and maintain an explicit audited exception registry, never a blanket exemption. Prefer Bangla transliteration for user-facing brand/product names. CMS requires locale-complete publication: a page cannot publish a locale with incomplete copy, and a translation cannot silently borrow the other language. CI validates keys, CMS fixtures and generated public output in both directions; editor preview flags mixed-script content. Hreflang links only between equivalent published translations. Human editors must review Bangla quality; machine translation alone is insufficient.

## Design, responsive UX and accessibility

Use the [portfolio audit](SITE-AUDIT.md) as a **color-grading** input: near-black, warm off-white and restrained green. Define independent OnSkillIT type, spacing, layout and component tokens for public, admin and portals. **Confirmed:** dark and light themes with a visible toggle on every interface. Both themes retain the recognizable green grading, but light surfaces use purpose-designed contrast rather than an inverted dark palette. Respect system preference initially, persist the explicit user choice across sessions, render the chosen theme before paint to avoid flash, and keep the toggle labeled and keyboard accessible. Theme must not change content or permissions. Proposed spacing scale 4/8/12/16/24/32/48/64, fluid type, 12-column desktop with mobile-first collapse. Inventory: buttons, forms, cards, responsive tables, navigation, dialogs/drawers, tabs, badges, alerts, progress, loading/empty/error/success and focus states. Admin and CMS need usable mobile review/editing; course learning needs narrow-screen navigation and stable progress. Target WCAG 2.2 AA, keyboard operation, visible focus, labels/error summaries, contrast, screen reader announcements, reduced motion and ≥44×44 CSS px touch targets where feasible. [WCAG 2.2](https://www.w3.org/TR/WCAG22/).

**Independent motion and interaction concept:** OnSkillIT uses a calm “guided progress” language. Public pages scroll normally; course discovery filters update with immediate status feedback; cards use subtle elevation/color change; primary actions acknowledge state in place; learning progress animates only after confirmed completion; schedules use clear expand/collapse and timeline transitions; admin tables favor instant, stable state changes over decorative movement. Proposed durations: feedback 120–180ms, panel transitions 180–240ms, route/section entrance 240–320ms, all using opacity/transform where possible. No scroll hijacking, magnetic cursor, page-turn gestures, particle wordmark or moving geographic background. Motion never conveys the only status signal; reduced-motion mode removes nonessential animation. These timing values are design hypotheses to validate with a prototype and user review, not inherited portfolio constants.

**Design acceptance gate:** before development, review an original visual concept covering homepage, service detail, course detail, learning view, staff dashboard and mobile navigation. Confirm visual distinction from both the old template and the portfolio, content hierarchy at 360px and desktop widths, keyboard/reduced-motion behavior, contrast, real Bangla type rendering, and complete loading/error/empty/success states. Aesthetic approval is a partner decision; accessibility and performance gates remain measurable regardless of taste.

**Responsive release gate:** every public, student, instructor, client, CMS and admin route must complete its main task at 320, 360, 390, 768, 1024, 1440 and ≥1920 CSS px, in portrait and landscape where meaningful. No horizontal page overflow, clipped essential content, hidden submit action, inaccessible table column, overlapping controls, broken dialog, or motion-induced layout shift. Tables may become labeled cards or controlled horizontal scrollers with sticky context. Forms must support mobile keyboards, validation recovery and saved draft state. Test 200%/400% zoom, long Bangla text, low-end mobile, touch and keyboard input, safe-area insets and reduced motion. A visual review plus GitHub browser automation and accessibility checks is required for each major template and state before release.

## Quality, operations, phases and acceptance

Proposed p75 mobile public CWV: LCP ≤2.5s, INP ≤200ms, CLS ≤0.1. Define load profile before p95 API target; proposed ≤500ms for ordinary reads. GitHub CI runs lint, types, unit/integration/API/DB/component/e2e, permission, security, accessibility, responsive and build checks; staging runs smoke, performance, payment sandbox and restore drill. No local builds/tests. Production release requires owner gate. Backups cover encrypted DB/media/config with offsite retention; proposed RPO 24h and RTO 8h require business approval. Logs/metrics/traces/uptime/deployment IDs exclude secrets and private payloads.

The canonical phase sequence, dependencies and gates are in `PHASES.md`; page IDs and routes are in `PAGES.md`. Phase 0 is documentation only. V1 implementation runs through PHASE-14, with PHASE-15 reserved for approved future evolution. Every phase updates docs and traceability with GitHub CI evidence. Acceptance examples: duplicate normalized contact rejected; sub-admin cannot grant beyond scope; content publish creates revision and SEO output; batch capacity survives concurrent enrollments; instructor cannot grade unassigned batch; replayed payment callback cannot duplicate a transaction; backup restore meets approved recovery objective.
