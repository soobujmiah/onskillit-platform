Added on `phase-01/foundation-audit-scaffold`, continuing PR #7:

- `src/db/schema.ts`, `drizzle.config.ts` and the reviewed SQL pair `src/db/migrations/0001_foundation_probe/{up,down}.sql`: one infrastructure-only table (`foundation_probe`), not domain schema. `drizzle-orm` and `postgres` (postgres-js) are dependencies; `drizzle-kit` is a devDependency for future typed-schema tooling. `drizzle-kit` does not generate down-migrations, so the up/down pair is hand-authored per ADR 0006's "reviewed SQL migrations."
- `.github/workflows/database.yml`: a `postgres:17-alpine` service container applies `up.sql`, asserts the table, applies `down.sql`, asserts removal, reapplies `up.sql`, then builds/starts the web process against that synthetic database and asserts `GET /api/v1/health` reports `checks.database: "ok"`, then runs the worker directly (not via `npm run`, to keep signal delivery direct) under `timeout --preserve-status -s TERM 5s` and asserts both the "worker ready" log line and a clean (status 0) shutdown after SIGTERM — `--preserve-status` matters here: without it `timeout` reports its own 124 instead of the child's real exit code whenever it fires the signal (see the fix note below).
- `src/app/api/v1/health/route.ts`, `src/db/client.ts`: the health route now attempts `select 1` when `DATABASE_URL` is set and reports `checks.database`; when unset (the existing `web` job) it returns exactly the prior liveness-only body, so that job's assertions are unchanged.
- `src/worker/index.ts`: a minimal separately-runnable worker process — connects to Postgres if configured, logs a structured ready line, handles SIGTERM/SIGINT for graceful shutdown, and runs a heartbeat placeholder. It deliberately does **not** implement outbox job claiming/leasing: there is no `OutboxEvent` table yet, and that logic belongs to whichever later phase first writes to the outbox (see DATA-MODEL.md). `package.json` adds a `worker` script and a `tsx` devDependency to run the TypeScript entrypoint directly.
- `Dockerfile`, `docker/entrypoint.sh`, `.dockerignore`, `public/.gitkeep`: a multi-stage build on the existing `output: "standalone"` config produces one versioned OCI image; `PROCESS_ROLE=worker` at `docker run` time selects the worker entrypoint instead of the web process, matching ADR 0006/0009's "one versioned OCI artifact, separately deployable worker."
- `.github/workflows/container.yml`: builds that image, runs the web container on an isolated Docker network and curls its health/home routes, then separately runs the worker container and confirms its ready log via `docker logs`, using `docker stop`/`docker rm -f` (not a foreground `timeout`) so container cleanup cannot hang the job regardless of how the entrypoint's PID 1 handles signals. This is an ephemeral-runner, ephemeral-container "isolated preview/deploy smoke" — it proves the artifact builds and runs, not that it is reachable on any live host. No external preview/staging provider account exists or was created for this.
- `docs/OPERATIONS.md`: added a dated least-privilege secret review — all four workflows declare `permissions: contents: read` only, none references an Actions secret, and the Postgres service container's credentials are synthetic and job-scoped. Records the rule for whoever adds the first real secret later (GitHub Environment scoping, required reviewers, never exposed to forked-repo PRs).
- `docs/ARCHITECTURE.md`, `docs/DATA-MODEL.md`, `docs/API-CONTRACT.md`, `docs/TRACEABILITY.md`: implementation notes updated to match; `docs/HANDOFF.md` rewritten as the new canonical handoff.

Two problems surfaced only once real GitHub state was checked, not from reading the YAML:

- After the first push (`3d50f02`), zero Actions check-suites appeared for over 10 minutes, for any workflow — not just the new ones. Cause: `main` had advanced past this branch's `b3a9170` merge-base (another session's deterministic repo-knowledge-sync rollout), and a genuine conflict in `docs/OPERATIONS.md` (both sides appended a section) left the PR's `mergeable` as `CONFLICTING`. GitHub cannot build the `refs/pull/7/merge` ref a `pull_request` workflow needs when that's true, so nothing queues — with no error surfaced via the API. Fixed with `git merge origin/main` (commit `b067305`), keeping both OPERATIONS.md sections. Caught mid-merge: this branch's `.gitignore` has a blanket `*.sql` rule that had silently kept `src/db/migrations/0001_foundation_probe/{up,down}.sql` out of the very first commit (`database.yml` would have referenced files that were never pushed); fixed with a `!src/db/migrations/**/*.sql` negation before re-adding them.
- Once CI actually ran, `Database` failed once: the worker-shutdown assertion read `timeout`'s own exit code, which is 124 whenever it fires the signal by default — regardless of the child's real exit status. The worker itself shut down cleanly (both "worker ready" and "worker shutting down" logged; see run [36475280740](https://github.com/soobujmiah/onskillit-platform/actions/runs/36475280740)). Fixed with `timeout --preserve-status` (commit `594f604`).
